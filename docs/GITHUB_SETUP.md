# GitHub для пяти участников и их агентов

Подготовлено 22 ноября 2026. Известный аккаунт владельца: StefBliz.
Организация: https://github.com/orbitguard-team
Репозиторий: https://github.com/orbitguard-team/orbitguard
Project: https://github.com/orgs/orbitguard-team/projects/1/views/1
Организация, закрытый репозиторий и Project созданы. Issues пока не опубликованы.
Документы подготовлены для ветки codex/docs. Шаги создания ниже оставлены как справка;
повторно создавать организацию и репозиторий не нужно.

## 1. Создать организацию

Войди на github.com под StefBliz. Открой аватар → Settings → Organizations → New organization.
Выбери GitHub Free, предложенное свободное имя orbitguard-team, свой контактный email,
укажи, что организация принадлежит твоему личному аккаунту, и заверши форму.
Если имя занято, можно использовать chuykinteam-orbitguard.
Организация — общий владелец ресурсов; репозиторий — код и задачи; Project — доска задач.

## 2. Репозиторий и команда

В организации: Repositories → New repository → orbitguard → Private → Create repository.
Если будешь загружать локальную папку через Git, оставь удалённый репозиторий пустым.
Не добавляй второй README при создании.

People → Invite member: пригласи остальных четырёх по их логинам; приглашения надо принять.
Teams → New team → developers: добавь пять участников; дай этой команде Write на orbitguard.
Владельцем организации остаётся StefBliz; всем выдавать Owner не нужно.
Резервного владельца можно выбрать из команды отдельно.

Загрузи подготовленные файлы с сохранением папок .github и docs.
Для агента, работающего в этой локальной папке: сначала git status, git remote -v и проверка текущей ветки;
не переинициализировать существующий .git, не затирать существующий remote/историю.
Затем связать папку с фактическим URL пустого репозитория, сделать первый commit и push в main.
Это первый служебный push; последующий код идёт через PR.

## 3. Доска

На странице ОРГАНИЗАЦИИ: Projects → New project → Board.
Название: OrbitGuard — MVP к 29 ноября. Выбери импорт задач из orbitguard, если доступен.
Project принадлежит организации; он не является папкой внутри репозитория.

В поле Status установи четыре значения:

| Status | Когда используется |
|---|---|
| To-do | Задача сформулирована, ещё не взята |
| In process | Есть один исполнитель, работа началась |
| In review | PR готов и ожидает проверки |
| Done | PR принят и результат проверен в main |

Группируй Board по Status. Добавь поля Priority (P0/P1/P2), Area, Target date;
используй стандартное Assignees для владельца. Зависимости указывай ссылками в issue.
Поставь доступ Project для developers: Write. Доступ к репозиторию и Project проверяются отдельно.
В orbitguard → Projects → Link a project привяжи эту доску.

Для начала одна карточка = один issue, PR связывается через Closes #N.
Не создавай отдельные карточки issue и его PR без необходимости.
Добавляй issues через Add item; включи auto-add для своего репозитория, если доступно.
При наличии подходящего встроенного workflow настрой закрытие выполненного issue → Done.
In process и In review сначала меняйте вручную или поручайте агенту с доступом к Project.
Связь с PR сама по себе не гарантирует автоматическое изменение статуса связанного issue.
Проверь переходы на одной пробной задаче до массового использования.

## 4. Правило одного approval

Требуемая политика: main обновляется только через PR, один независимый approval,
успешный CI и завершённые обсуждения. После изменений в коде старое approval сбрасывается.
Настройка при доступности: repository Settings → Branches / Rules → защита main,
Require pull request, Required approvals = 1, Dismiss stale approvals,
Require conversation resolution; после создания CI добавь его реальное имя в Required status checks.
Не требуй несуществующий check. Запрети force push и удаление main; отключи обход правил, где доступно.

Ограничение тарифа: обязательная защита веток доступна на Free для PUBLIC-репозиториев;
для PRIVATE-репозитория организации нужен Team или Enterprise. Закрытый Free подходит для старта,
но правило review тогда соблюдается командой вручную. Покупку тарифа или публикацию репозитория
решает владелец; не меняйте видимость ради настройки без его согласия.

Для маленькой команды назначьте интегратора: предложение — StefBliz.
Он делает Squash and merge после проверки условий. Для его PR ревью делает другой участник.
Это роль в процессе, а не техническая гарантия ограничения merge на Free private.

## 5. Что делает каждый сокомандник

1. Создаёт СВОЙ аккаунт GitHub, принимает приглашение и проверяет доступ к репозиторию и доске.
2. Клонирует общий репозиторий в свою локальную папку и открывает её в своём агенте.
3. Даёт агенту доступ к GitHub под СВОИМ аккаунтом: через поддерживаемое подключение или GitHub CLI.
   Для CLI после установки: gh auth login, затем gh auth status. Токен в чат не присылать.
   Для изменения Projects CLI может потребоваться отдельное разрешение project.
4. Просит агента прочитать AGENTS.md и выполнить назначенный issue.
5. Проверяет результат работы своего агента и отвечает на вопросы команды в GitHub.

Не используйте один аккаунт на всех. Агент действует от имени подключённого аккаунта;
два агента одного автора не могут дать его PR независимое засчитываемое approval.
Автоматическое ревью GitHub Copilot не заменяет требуемое approval участника.

## 6. Готовые промпты

Первый запуск каждого участника (подставить ФАКТИЧЕСКИЙ OWNER/REPO):

```text
Работаем в OWNER/REPO над OrbitGuard. Прочитай AGENTS.md, README.md и docs/PLAN.md.
Проверь текущий checkout, GitHub-аккаунт и доступ к issues, PR и Project.
Пока не меняй код. Сообщи, готов ли ты брать задачи и какие доступы отсутствуют.
```

Взять задачу:

```text
Выполни issue #N в OWNER/REPO по AGENTS.md. Прочитай обсуждение и зависимости,
проверь, что задача свободна, закрепи за моим аккаунтом и отметь In process.
Создай отдельную ветку, реализуй критерии приёмки, проверь результат.
Публикуй относящиеся к задаче вопросы и прогресс в issue.
Открой PR с Closes #N, запроси review у @REVIEWER и отметь In review.
Не выполняй merge. Верни ссылку на PR и результаты проверок.
```

Ревью (давать ДРУГОМУ участнику):

```text
Сделай ревью PR #N в OWNER/REPO по AGENTS.md. Прочитай связанный issue,
проверь актуальный diff и критерии приёмки, запусти нужные проверки.
Опубликуй конкретные замечания в PR. Если есть существенные ошибки — Request changes;
если их нет — Approve с перечнем проверок и ограничений. Не делай merge.
```

Комбинированный запуск:

```text
В OWNER/REPO сначала сделай ревью чужого PR #M по AGENTS.md,
затем выполни назначенный мне issue #N и открой PR. Для ревью и реализации
используй изолированные рабочие копии, если иначе будут смешиваться изменения.
```

GitHub хранит общую историю, но не запускает чужого агента от комментария автоматически.
Участник открывает агента и поручает прочитать новые сообщения/review.

## 7. Загрузить задачи

После выбора пути MVP создай отдельный issue для каждого блока docs/BACKLOG.md:
заголовок, описание, критерии, исполнитель, ссылки на зависимости; добавь его в Project.
OG-01 и подобные — локальные идентификаторы плана, а не реальные номера GitHub.
После создания замени зависимости OG-xx ссылками #N. GitHub сам присваивает номера,
общие для issues и PR. Не обещай, что OG-01 окажется issue #1.

## Проверка настройки

- Все пять участников видят репозиторий и Project.
- Пробный issue виден в To-do и имеет одного assignee.
- Другой участник может открыть PR и получить review не от автора.
- После merge связанный issue закрывается; карточка получает Done.
- Каждый агент видит AGENTS.md и может читать комментарии.
